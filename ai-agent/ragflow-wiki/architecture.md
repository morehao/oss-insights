# 系统架构

RAGFlow 看起来是一整套产品，但它的结构可以归结为一句话：**同一个服务程序，按不同角色启动，围绕同一套存储与检索引擎协作**。理解这一点，后面所有的"服务""进程""引擎"就都能各归其位。

## 分层视角

从外到内，RAGFlow 可以分成四层：用户从**接入层**进入；请求由**进程角色层**里的某个角色接收；实际工作交给**核心引擎层**处理；最终数据落在**基础设施层**。下图给出这四层的内容与请求自上而下的方向。

![RAGFlow 系统分层与请求主链路](assets/architecture.svg)

看图时按"自上而下"读：最上面是用户接触到的入口，最下面是所有数据最终落地的地方。同一个方框层内的模块是并列关系，层与层之间不是一一对应，只是说明它们分别属于哪个层面。

| 层 | 包含什么 | 作用 |
|------|----------|------|
| 接入层 | Web 控制台、REST API 与 CLI、客户端 SDK 与机器人通道 | 用户与外部系统进入系统的入口 |
| 进程角色层 | Admin、API、Ingestor、Syncer、DeepDoc | 同一程序的五种运行角色，各自承担一类工作 |
| 核心引擎层 | 文档摄取流水线、Agent 运行时、检索与重排、DeepDoc 解析、RAG 生成 | 真正干活的能力模块 |
| 基础设施层 | 文档检索引擎、关系数据库与缓存、消息/对象存储/列式库 | 被各层共享的外部依赖，数据最终落在这里 |

## 一次请求的路径

以一个"提问"为例，请求的流向是：客户端经接入层发出 HTTP 请求，由 **API 角色**接收；API 把请求交给路由分发到对应处理逻辑，再由服务层组织业务，最后调用核心引擎层（检索、重排、RAG 生成）完成工作，并从基础设施层读写数据后返回结果。

这条路径的关键在于：**接入层只负责接收，真正的能力都在引擎层**。因此无论请求来自 Web 控制台、CLI 还是 SDK，走到的都是同一套处理与检索逻辑。

## 一个程序，多种角色

RAGFlow 的后端只有一个命令入口，用不同的启动参数决定它扮演哪种角色。不指定角色时，默认以 **API** 角色启动。由于这些角色参数共用同一个变量，**同时传入多个时最后一个生效**。

| 角色 | 承担的工作 |
|------|------------|
| API | 对外的在线接口，接收并处理业务请求（默认角色） |
| Admin | 管理侧进程，负责初始化与运维类操作 |
| Ingestor | 负责文档摄取，把文档解析、切分、入库 |
| Syncer | 负责从外部数据源同步文档 |
| DeepDoc | 负责文档解析推理 |
| Migrate | 只执行数据库迁移，完成后即退出 |

其中 **Migrate** 是个例外：它不启动任何常驻服务，做完数据库迁移就退出，因此可以在其他角色启动之前先跑一遍。数据库初始化、文档检索引擎、缓存、对象存储与消息队列的初始化，则是各常驻角色启动时的公共步骤。

## 模块地图

后端代码集中在 `internal/` 下，按职责分目录，主线大致是"路由 → 处理 → 服务 → 引擎 → 存储"：

- **入口与分发**：`cmd/` 是命令入口；`internal/router/` 负责把 HTTP 路径分发到对应处理；`internal/handler/` 是各接口的处理逻辑。
- **业务与数据**：`internal/service/` 组织业务逻辑；`internal/dao/` 负责数据库访问；`internal/entity/` 定义数据实体。
- **核心能力**：`internal/ingestion/` 是文档摄取流水线；`internal/agent/` 是 Agent 运行时与组件；`internal/deepdoc/` 与 `internal/parser/` 负责文档解析；`internal/rag/` 是检索与生成相关逻辑。
- **外部依赖封装**：`internal/engine/` 抽象文档检索引擎；`internal/storage/` 封装对象存储；`internal/syncer/` 是数据源同步服务；`internal/channels/` 是即时通讯通道；`internal/tokenizer/` 负责分词。
- **其他**：`internal/admin/`、`internal/cli/`、`internal/mcp/`、`internal/utility/` 等提供管理、命令行、协议适配与通用工具。

前端代码在 `web/`，是独立的 React 应用，通过 REST API 与后端交互。
